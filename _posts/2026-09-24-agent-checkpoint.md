今天结合 Codex 和 Claude Code 的官方技术文档，梳理了 Agent 开发中的 checkpoint（检查点）概念。

## 核心理解

Checkpoint 是 Agent 执行过程中的存档点：保存某个时刻的必要状态，为后续恢复、回退或分叉探索提供依据。它与模型训练中保存权重的 checkpoint 属于不同层面。

判断一种 checkpoint 能力是否有用，不能只看有没有“恢复”按钮，更要看：**保存了什么，恢复了什么，哪些操作无法撤销。**

## Agent 需要保存哪些状态？

从工程设计角度，可以将状态分为三层。这是理解问题的分析框架，并非两家产品共同定义的标准。

| 状态层 | 典型内容 | 恢复时要注意什么 |
| --- | --- | --- |
| 对话状态 | 消息、工具调用结果、上下文摘要 | 对话回退不代表文件回退 |
| 执行状态 | 当前步骤、已完成任务、待处理审批 | 中断的工具操作可能已经产生效果 |
| 环境状态 | 文件、数据库、远程资源 | 外部变化可能无法随检查点撤销 |

例如，Agent 重构代码失败后，如果只恢复旧对话，文件仍是修改后的版本，就可能产生状态错位。可靠的恢复机制必须明确这些状态之间的对应关系。

## Claude Code：文件恢复与对话恢复可以分开

Claude Code 会为启动新一轮执行的用户提示创建检查点，跟踪自身文件编辑工具的修改。通过 `/rewind` 可以选择恢复代码、恢复对话，或同时恢复两者。Bash 命令造成的文件修改不属于这一跟踪范围。[官方说明](https://code.claude.com/docs/en/checkpointing)

Claude Agent SDK 提供 `enableFileCheckpointing` 和 `rewindFiles()`；Python 对应名称是 `enable_file_checkpointing` 和 `rewind_files()`。SDK 的文件回退只恢复文件，保留对话历史。因此可以撤销错误代码，同时保留失败过程供后续分析。[SDK 文档](https://code.claude.com/docs/en/agent-sdk/file-checkpointing)

## Codex：区分恢复会话、分叉与历史回退

Codex App Server 将几种操作分别定义：

- `thread/resume`：继续已保存的会话。
- `thread/fork`：复制历史到新会话，可用 `lastTurnId` 指定分叉位置。
- `thread/rollback`：移除最近若干轮上下文并记录回退标记；查阅时的文档已将它标为弃用。

这些接口的会话语义，不能被理解为文件、进程、数据库也会一并恢复。基于 Codex 构建需要环境回滚的 Agent 时，应另外管理工作区快照，并将它与会话位置关联。[App Server 文档](https://learn.chatgpt.com/docs/app-server)

## 开发中最值得注意的两个问题

**第一，选择清晰的保存边界。** 例如，在工具结果已经记录、文件快照已经保存、下一步尚未开始时建立检查点。若允许在操作执行中恢复，就需要额外处理操作状态的不确定性。

**第二，防止外部操作重复执行。** 假设 Agent 成功创建远程工单，但在保存结果前崩溃。恢复后直接重试，可能创建重复工单。检查点本身解决不了这个问题，还需要幂等键、操作结果查询或补偿机制。已发送的邮件也不会因为对话回退而被自动撤回。

这些是从上述能力边界引出的通用工程设计建议，并非两家产品已经提供完整事务恢复的承诺。

## 与几个相近概念的区别

| 概念 | 主要回答的问题 |
| --- | --- |
| 日志 / Trace | 刚才发生了什么？ |
| Memory | 什么信息值得长期记住？ |
| 上下文压缩 | 如何减少模型当前需要读取的历史内容？ |
| Git commit | 被追踪的文件处于什么版本？ |
| Checkpoint | 能回到哪个位置，并恢复哪些状态？ |

## 今天的收获

Checkpoint 的价值在于降低长任务中断和试错的成本。选择或设计 Agent 框架时，我会优先检查四点：**保存范围、创建时机、恢复语义、外部操作的重复执行风险。**
